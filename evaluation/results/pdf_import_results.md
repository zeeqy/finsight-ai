# PDF e-statement import: results (4 Nov 2026)

Module 1 now reads the monthly PDF e-statements banks email to customers, as well as CSV and XLSX exports. This was added because most users do not know where to download a CSV, and many banks do not offer one, while the PDF arrives every month without asking.

## How it works

- `server/src/services/pdfStatement.js` reads the text and its position on each page (pdf.js 5.7.284, in Express; nothing leaves the server).
- The table is found from its header line (Date ... Balance, or Tarikh ... Baki). A line that starts with a date in the date column begins a transaction, and the indented lines under it complete its description.
- **Money in or out is decided by the running balance:** previous balance minus the amount equals the new balance means money out. The column position is only a fallback.
- **Every row that does not add up is reported in the preview,** never hidden.
- **Reference numbers and bank codes are removed** from descriptions, for example R97435, XEPL339, 16-digit FPX references and UUIDs.
- **Bank Islam only:** its layout prints the account holder's name under every outgoing payment. That name is removed from money out, so ordinary payments are not mistaken for transfers to the user's own account.
- **Locked PDFs:** the password goes with the upload and is used once to open the file. It is never stored or logged.
- **Preview before saving:** the upload dialog first shows the bank, the period, the number of transactions, how many are already imported, the balance checks and the first rows. Nothing is saved until the user presses Import.
- **Imported rows reuse the CSV pipeline:** duplicate check, the ML categoriser (Logistic Regression + rules) and anomaly flags.

- **First run:** 3 Bank Islam rows failed the check, which found two bugs. Bank Islam prints 50 sen as ".50" with no leading zero, and the final summary page wiped out the column positions. Both are fixed, and the unit tests now cover them.
- **Re-uploading an imported statement:** the preview reports 0 new and 75 already imported, so nothing is counted twice.
- **Same month as CSV and PDF:** the two formats word descriptions differently, so a row is also treated as already imported when an unused stored row has the same day, amount and direction (`services/statementDedupe.js`). Each stored row matches one new row only. Tested on made-up files (unit tests, functional M1-30) and on a real pair: Bank Islam July 2026 as the CASATIA CSV and as the PDF e-statement, in both orders. The first file imported 75 rows; the second found 0 new and matched all 75 from the other file. Five genuine pairs of same-day payments of the same amount were kept, because each stored row matches only once. A genuinely new payment is only missed if a different payment with the same day, amount and direction is already stored and not matched by anything else.
- **Categoriser on the 312 rows:**
  - 130 rows: model, confident;
  - 109 rows: model, low confidence (marked "?" in the ledger for the user to check);
  - 32 rows: keyword rules;
  - 49 rows: money in, set by direction.
- **Categoriser accuracy is not measured on these statements,** because they are not hand-labelled. Many rows are DuitNow QR payments to small sellers or friends, and CIMB prints "QR Payment" with no merchant name. That is the main reason for the low-confidence share.

## Automated tests

- **Unit** (`server/test/pdfStatement.test.js`, 7 tests): rows, direction and all checks; descriptions without reference numbers; the Bank Islam name rule; several pages; a wrong amount reported; a locked file (no password, wrong password, right password); not a PDF, and a PDF with no table.
  - The test PDFs are made up and generated by `server/scripts/makeStatementPdf.js`, locked where needed with the PDF standard 40-bit RC4 handler. No real statement is used.
- **Functional:**
  - **M1-28 (locked PDF):** password asked for, wrong password rejected, preview saves nothing and all rows match, import adds 5, a second preview finds 0 new.
  - **M1-29:** a broken file and a PDF with no table both return 422, and nothing is saved.
- **UI check:** in the browser, on a made-up locked PDF: password prompt, wrong-password message, preview with checks and first rows. At 375 px there is no sideways scroll; on phones the date moves under the description.

## Limits

- **Tested layouts:** only CIMB (Savings Account-i) and Bank Islam (Savings Account). Maybank and other banks go through the same general reader, but no real PDF from them has been tested. The upload help says so.
- **Credit cards:** credit-card statements usually have no balance column. The reader finds the table by its Date and Balance headings, so it reports that no transaction table was found. Credit cards are not supported.
- **Scanned PDFs:** a PDF that is a scan or photo has no text, so it is rejected with a message. There is no OCR.
- **Two accounts:**
  - *Money out:* a transfer from one of the user's accounts to another counts as saving, not spending (existing own-name rule).
  - *Money in:* the matching deposit in the second account is still categorised as money in. Declared income is used first, so the surplus is unaffected, but "money in" totals can be overstated.
- **Bank Islam holder name:** the rule assumes the name is printed the same way as at the top of page 1.
